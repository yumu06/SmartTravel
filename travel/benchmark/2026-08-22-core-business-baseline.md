# 核心业务性能基线与推荐索引优化

日期：2026-08-22

## 环境与隔离

- 服务：本机 Windows，Go/Gin，基准端口 `1017`；原服务 `1016` 全程保持监听。
- 数据库：仅重建 `travel_benchmark` 的业务表；`travel_database` 保持存在且未执行删除、清空或迁移。
- 数据量：1,000 用户、10,000 文章、50,000 评论、100,000 点赞、30,000 收藏、10,000 足迹。
- 鉴权：独立临时 JWT 密钥、固定基准用户 1、真实 Redis Session；Token 和所有密码均未写入报告。
- 访问日志：1017 的逐请求访问日志关闭，保留错误和 200ms 慢 SQL 日志。
- 延迟口径：当前 Go 压测器记录收到 HTTP 响应头所需时间（TTFB），并读取完整响应体后复用连接。
- 阶梯：并发 10 使用 500 请求；并发 50/100/200 使用 5,000 请求；错误率达到 1% 时停止升压。

四个接口的单请求冒烟均返回 HTTP 200，压测结束后健康检查仍为 HTTP 200。

## 证据

优化前推荐查询：

```sql
SELECT * FROM posts
WHERE user_id <> 1
ORDER BY like_count DESC, view_count DESC, created_at DESC
LIMIT 20;
```

`EXPLAIN` 显示 `type=ALL`、预计扫描 9,808 行，并出现 `Using where; Using filesort`。整轮基线日志包含 4,239 条慢 SQL，其中推荐查询 2,848 条、鉴权用户主键查询 1,393 条。

两次孤立的 HTTP 401 都远低于 1% 停止阈值，且下一档并发恢复为零错误。中间件会把 Redis 校验或 MySQL 用户查询的任何错误统一转换为 401；现有日志不足以区分具体依赖，不能把它归因于 Token 失效。

## 已实施优化：推荐排序复合索引

为 `posts` 增加与排序一致的降序索引：

```text
idx_post_recommend(like_count DESC, view_count DESC, created_at DESC)
```

回归测试验证索引名称、字段顺序和降序方向。迁移后 `EXPLAIN` 使用 `idx_post_recommend`，预计仅扫描 39 行，不再 filesort。

## 剩余瓶颈排序

1. **鉴权用户查询**：每个受保护请求都访问 MySQL；用户信息接口随后又按 OpenID 查询一次。高负载推荐阶段出现 1,393 条主键查询慢日志。下一步应为鉴权身份增加短 TTL Redis 缓存，并保留用户禁用/删除后的失效策略。
2. **文章详情读写放大**：每次读取详情前同步执行一次 `view_count + 1`，使纯读接口变成行写入；热点文章会产生锁竞争。下一步应将浏览计数写入 Redis 增量并批量回写 MySQL。
3. **错误可观测性**：鉴权依赖失败与无效 Token 都返回 401，导致孤立错误无法归因。下一步应区分凭证无效、Redis 不可用和数据库失败，并增加不含敏感数据的分类指标。
4. **推荐结果缓存**：索引已满足当前 10,000 文章规模和 P95 目标；数据量继续增长时，可为候选结果增加短 TTL 缓存，但应在索引收益之后独立验证。

## 复现

使用环境变量注入 MySQL、Redis 与临时 JWT 配置后：

```powershell
go run ./cmd/benchmark-setup
.\benchmark\run_core_baseline.ps1
.\benchmark\run_core_baseline.ps1 -Scenario recommendation
```

脚本不会打印 Token 或 JWT 密钥。`benchmark/post_ids.txt` 仅包含基准文章 UUID。
